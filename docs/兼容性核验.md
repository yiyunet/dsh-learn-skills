## 二、可独立实现 vs 必须改宿主

| 功能 | 归属 | 说明 |
|---|---|---|
| 输入区按钮与菜单 | **插件可独立实现** | 用 `conversation.input.left` 这一**已存在**的 list 槽位；无需 DOM 注入、无需改宿主 |
| 六轮问答界面 | **插件可独立实现** | 复用宿主 `user-questions/request` 瀑布（`packages/client/ui-user-questions/src/client/index.ts:105`），本插件只订阅事件显示状态 |
| 斜杠命令 `/learn` | **插件可独立实现** | `ctx.commands.register`（`packages/interaction/commands/src/index.ts`），base bundle 已挂 `commands` 行 |
| 预设创建 | **插件可独立实现**（写 bundle；**安装交人**） | 写 `<工作区>/.dsh/preset-bundles/<id>/` 两件套（`package.json` + `cordis.patch.yml`，官方 SKILL 原文 "exactly two files"）；**安装不由插件代做** —— 官方入口 `plugin_manager` 强制审批、而服务方法无审批闸，代装＝替用户越权。插件只出可复制的指引 |
| 预设热更新到当前会话 | **不可实现（宿主约束）** | standing mount 一进程一次 + 只允许空会话切换；这是宿主设计，不是缺扩展点。插件改为提示"新建会话" |
| 读模型可见的 system prompt | **不可实现（宿主未暴露）** | 体检第 3 项因此固定标 `inaccessible`，不猜 |
| 读长期记忆 | **不可实现（宿主未暴露）** | 体检第 8 项同样标 `inaccessible` |
| 会话消息读取 | **插件可独立实现（按会话 API）** | 插件通过 `ctx.get('agents')` 取 live agent 的 session 事件；拿不到就标"无法访问" |

> **结论：本升级不需要任何宿主补丁。** 全部界面与运行时能力都落在既有正式扩展点上。
> 这也意味着**没有**"必须改宿主才能实现"的功能 —— 唯一的硬约束是"预设不在当前会话即时生效"，
> 那是宿主的语义设计，插件选择如实提示而不是绕过它。

## 三、版本兼容矩阵

### 先说清一件事：哪个字段才是真的

| 字段 | 谁读 | 是否强制 |
|---|---|---|
| `engines.dsh` | 官方 `@deepseek-ai/dsh-package-manifest` 的 `DshEnginesManifest` | 字段**在官方 schema 里**；但其注释自述 "Runtime requirements; DSH compatibility is **declarative until a reader enforces it**" ⇒ 目前**不被强制**，登记了也不会挡住不兼容版本 |
| `dsh.compatibility` | 生态约定（`@xmanrui/dsh-im`、`@yiyunet/dsh-dingtalk-connector` 同形） | **不在官方 `DshManifest` 里**（官方只有 `manifestVersion`/`bundle`/`profile`/`client`），全仓检索 `dshReleases` **零命中** ⇒ 纯信息字段，只用于人读与排障 |
| `dsh.client.inject` | 客户端构建/装载链 | 是清单字段，值为**运行时包名**（用于告知"我依赖这些客户端模块表项"） |

⚠️ **由此得出的一条重要结论**：**没有一个字段能替你挡住"装到不兼容的宿主上"**。
所以本插件把真正的门槛做在**运行时**：`inject = ['userQuestions','commands']` ——
依赖不满足时 cordis 让它**停在 inactive**，而不是带病运行。这是比版本号更可靠的判据。

`package.json` 里两个字段都写了（`engines.dsh: ">=0.1.5"` ＋ `dsh.compatibility`），
但**判据以运行时服务可用性为准**。
